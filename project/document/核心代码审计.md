## A. 编译器/检查器（正确性，最高优先）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| A1 ✅ | ~~**返回类型不检查**~~ 已修复：checker 校验 return 类型 | `func f(): int { return "abc"; }` 编译通过，运行输出 `6384336`（指针值被当 int） | 静默 UB，最危险 |
| A2 ✅ | ~~**非 void 函数缺 return 不检查**~~ 已修复：非 void 函数要求所有路径 return | `func f(): int { if (1==1) { return 5; } }` 编译通过；条件不成立时返回未定义值 | 静默 UB |
| A3 ✅ | ~~**字段/参数/返回类型名不校验**~~ 已修复：struct 字段/func/handler/controller/namespace/static/const 统一 check_type_name | `struct A { x: Nope; }` → C 编译错误 `';' expected (got "Nope")`；`func f(a: Nope)` → C 错误 `invalid type` | 错误信息差、语义泄漏到 C |
| A4 ✅ | ~~**重复声明静默合并**~~ 已修复：同一文件内重复声明报错 | 同文件两个 `func f`（返回 1/2）编译通过并打印 `1`；重复 struct/event/controller 同样 | driver 合并按 (类别,名) 去重保留第一个，用户改动被静默忽略 |
| A5 ✅ | ~~**break/continue 位置不检查**~~ 已修复：循环外报错 | 顶层 `break;` 通过 checker，C 编译报 `cannot break` | 应在 checker 报错 |
| A6 ✅ | ~~**容器字面量作实参**~~ 已改为明确的 checker 错误（暂不支持，提示先赋给变量） | `sum([1,2,3])` → Python traceback `container literal only supported in var/assignment context` | 崩溃式错误，不是语言错误 |
| A7 | 整数除零/溢出未检查 | `print(1 / 0)` → 进程崩溃 `0xC0000094` | 无语言级错误 |
| A8 | JSON 失败直接 panic | `Json.parse(S, "not json")` → `well panic: JSON parse error at 0: bad null`，进程退出 | 无法恢复/降级 |
| A9 | 运行时 panic 无源码位置/调用栈 | `well_panic(msg)` 仅打印消息 | 线上定位困难 |
| A10 | 语言特性缺口 | 无 `switch`、异常/Result、泛型、接口、类型转换、`defer`、字符串插值 | 见路线图，非缺陷 |

**建议**：A1–A5 是低成本高收益，应立刻修；A6 转成 check error；A4 至少在单文件内报重复。

## B. 运行时核心

| # | 问题 | 说明 |
|---|---|---|
| B1 | **Cache 无容量上限/淘汰** | `well_cache_set` 只插入；没有 LRU/最大条数，长跑服务内存可能单调增长（除非业务 remove 或 TTL 清理开启） |
| B2 | **环回收依赖 TTL（默认关闭）** | 成环对象随 `WELL_MODEL_TTL_MS` 整组回收；默认关闭时环永久泄漏（文档已说明，但容易踩） |
| B3 | ~~对象池/模型清理热路径~~ **本轮已修** | `well_model_cleanup_if_due()` 每个调度循环调用，内部 2×`getenv` + 扫描 257 个池 class（持池锁）；改为 env 只读一次 + pool sweep 1s 节流后，单请求 min 40.7 → **34.2 µs**（raw C 基线 24.8，比值 ~1.38） |
| B4 | WellCtx 帧日志每次 handler 分配 | `ctx_push` 首次 realloc 8 个指针，任务结束 free；每任务至少一次 malloc/free，可改 TLS 复用缓冲 |
| B5 | Windows 条件变量 10ms 轮询 | `WaitForSingleObject(event, 10)` 假 cond；空闲线程 100 次/秒唤醒，高线程数下 CPU/延迟损耗 |
| B6 | 调度器单把 `g_sched_mutex` | 4 并发客户端聚合低于 raw C（受机器抖动影响，曾测 ~41–60k vs 67–86k）；per-worker 锁属结构性优化 |
| B7 | 对象注册表每次分配加锁 | `well_new` 都做 oid 分片插入，`well_release` 移除；高频分配（event/req/字符串外的结构）有锁开销 |
| B8 | 订阅节点不释放 | `well_off_type` 只置 inactive；反复 on/off 会积累 `WellSub`（进程级，通常可接受） |
| B9 | 阻塞 I/O 占用 worker | File/MySQL 同步调用在 worker 上执行，无让渡/超时；无 async/await |
| B10 | 序列化版本固定 1、无 schema 演进 | `WELL_SER_VERSION` 1；bad magic/version 直接 panic |
| B11 | JSON 只有 parse，无 stringify | 无 `Json.stringify`，无错误值版本 |
| B12 | POSIX 路径未在本机验证 | 本机只有 Windows tcc 编译通过；需 Linux CI |
| B13 | static 字段写无锁 | 已在文档声明"并发写由使用者负责"；启动期写入、运行期只读是推荐用法 |

## C. 性能与工程

- C1 无编译器优化 pass（常量折叠/DCE）；driver 调 tcc 未传优化参数（用户可 `WELL_CC=gcc/clang`，但 driver 不附加 `-O2`）。
- C2 每次 build 全量编译 runtime C（tcc 快，但无增量缓存）。
- C3 压测工具在 `tool_ai/tmp`，未入库；建议入库并加 `verify` 一键脚本（build + 76 用例 + C 测试 + 压测）。
- C4 无运行时指标（worker 利用率、steal 次数、队列长度、handler 耗时）与性能回归基线。

## D. 功能完整性（相对路线图）

- Store 仅 MemoryStore；Model 无二级索引/查询/事务。
- 容器：Map 无 `entries`，Array 无 `sort/reverse`；String 无 `replace` 等；仍按字节语义。
- 模块：无包管理/版本/热重载，module registry 无依赖顺序。
- Timer 精度约 5–15ms（轮询），无 cron/绝对时间 API。
- HTTP/WS/MySQL：测试暂缓（按要求）；MySQL 未事件化；无 TLS/chunked。
