## 0. 结论速览

**全绿 ≠ 正确。** 122 个用例全部是"正向最短路径"：不覆盖畸形输入、类型错配、长循环/泄漏、多 worker 并发、大报文、环状数据、深嵌套。本轮 **7 个 P0 全部落在这些空白处**，且都能从正常语言或网络路径触发。

| 级别 | 数量 | 含义 | 典型 |
|---|---|---|---|
| **P0** | **7** | 静默错误结果 / 内存破坏 / 可远程触发的进程崩溃 | 类型系统失守、栈破坏、堆溢出、栈溢出 |
| **P1** | **34** | 语义漏洞、资源泄漏、竞态、协议边界、诊断契约 | 泄漏 198976 对象、诊断无位置 |
| **P2** | **61** | 一般缺陷、文档/工程问题 | C 名称冲突、文档过时 |
| **P3** | **8** | 维护性 / 理论窗口 / 死代码 | Timer UAF 窗口 |

> 计数为 4 份分区报告表格合并、去重并含 Lead 纠偏后的结果（合计 110 条）。

### 四条主线

1. **检查器类型校验大面积失守（3 个 P0）** —— `var` 声明初始化、用户 `func` 实参、`const` 初始化三处**完全不校验**；`null`、运算符、`if` 条件也基本无规则。合法编译、运行期静默 UB 或段错误。多处只需一行 `check_assignable` 即可堵住。
2. **代码生成的作用域与生命周期（1 个 P0 + 6 个 P1）** —— 同名变量遮挡把 8 字节指针写进 4 字节 `int`（P0）；循环内 owned 临时对象、临时对象成员链、`for-of` 迭代源造成**确定性**泄漏（实测 shutdown 残留 198976 / 2000 / 7 个对象）。
3. **不可信输入下的递归与边界（3 个 P0）** —— JSON 未知字段跳过路径无深度限制、MemoryStore 环回读互递归、MySQL `queryJson` 结果缓冲堆溢出。分别对应 `Json.tryParse`（HTTP body 同构路径）、允许的环状 Model、任意 >1KB 字符串列。
4. **并发与协议边界（8 个 P1）** —— 字符串字面量全局表无锁（多 worker 可达堆破坏）、controller owner 栈非 TLS、WS 握手与超时、MySQL 无超时与池竞态、HTTP slowloris。

### 如果只修三件事

1. **FE-P0-2 / FE-P0-1 / FE-P0-3**：前端三处类型校验（半天内可完成，直接消灭最广的一类静默 UB）。
2. **M1**：MySQL `queryJson` 写前扩容（一个查询超过 1KB 即堆损坏）。
3. **R-01 / R-02**：JSON 跳过路径与 Store 回读的递归深度/环保护（不可信输入可直接打崩进程）。

### 1.2 逐条说明（含真实复现）

#### FE-P0-2 带注解 `var` 初始化不校验类型（影响面最大）

```python
# checker.py:337-352（VarDecl 分支）
if s.type: ty = s.type.name; self.check_type_name(ty)
if ty and isinstance(s.init, (ArrayLit, ObjectLit)):
    self.check_container_literal(...)          # 只有容器字面量走这里
else:
    et = self.check_expr(s.init, env)          # et 算出来后被丢弃
# 从未调用 check_assignable(ty, et)
```

复现（`python wellc.py check` exit 0，`run` 结果）：

| 程序 | run 输出 |
|---|---|
| `var x: int = "hello"; print(x);` | `8917600`（指针低 32 位；每次构建数值不同） |
| `var s: String = 123; print(s.length);` | 退出码 `0xC0000005`（访问违例） |
| `struct S{x:int;} var s: S = 42; print(s.x);` | 退出码 `0xFFFFFFFF`（野指针，无 panic） |

生成 C 直接是 `int x = well_string_lit("hello");` / `WellString* s = 123;`，TinyCC 只给 warning。
**影响**：最常用的声明形式把类型系统开了个口子，任意指针/结构体可进任意变量。
**建议**：在 `checker.py:346` 之后补 `self.check_assignable(ty, et)`（容器字面量分支保留），并加 3 条编译错误用例。

#### FE-P0-1 用户 `func` 调用不校验实参类型

```python
# checker.py:1582-1590（if name in self.funcs）
for i, a in enumerate(e.args):
    self.check_expr(a, env)      # 只求类型，丢弃结果
e.ty = f.ret.name if f.ret else "void"
```

对比 `namespace/static` 调用（`:1572-1578`）确实调用了 `check_assignable` —— 说明是遗漏而非设计。
复现：`func add(a:int,b:int):int{...}` + `print(add("x","y"));` → check exit 0，run 输出 `18359856`。
**建议**：与 namespace 分支一致，逐参数 `check_assignable(f.params[i][1].name, at)`。

#### FE-P0-3 `const` 零校验 + 文本宏重复求值

`checker.py` 从不检查 `ConstDecl.value`；`codegen.py:1242-1247` 把 const 生成为文本宏：

```c
#define C (new_S(ctx, ctx->oid))     // 每次引用都重新执行
```

复现：

```we
struct S { x: int; }
const C: S = new S();
controller Main { run() { C.x = 1; print(C.x); } }   // 输出 0（写进临时对象）
```

`const X: int = "str"` → run `8589920`；`const T: long = Host.nowMs()` 每次取新时间。
**建议**：const 只允许编译期常量表达式（字面量/常量运算/枚举成员）并 `check_assignable`；否则改"只读变量"语义、codegen 只求值一次。

#### CG-01 变量遮挡导致栈破坏

现象：外壳 `int x` → 内层块 `var x: String = "shadow"` → 块结束后 `x = 5;`。`self.env` 是函数级 dict，块退出不恢复，`gen_assign` 按内层 `String` 生成：

```c
WellString* _v = 5;
well_ctx_replace(ctx, (void**)&x, (void*)_v, 0);   // &x 是 4 字节 int 的地址
```

`well_ctx_replace` 内部写 8 字节指针 → 越界写栈。实测：打印 `shadow` 后进程崩溃（`EXIT=-1`）。
**建议**：块/循环/if/handler 体保存并恢复 `env`（或作用域链），并在 `gen_assign` 校验目标声明类型。

#### M1 `queryJson` 结果缓冲堆溢出（模块唯一 P0）

```c
size_t cap = 1024, len = 0; char *buf = malloc(cap);      // :295
for (j = 0; val && val[j]; j++) { ... buf[len++] = ch; }  // :334-340 写前无检查
if (len + 64 >= cap) { cap *= 2; buf = realloc(buf, cap); }  // :345 写完之后，且只翻一次
```

真实 MySQL 复现（本机 3306）：

```
SELECT REPEAT('a',2000) AS big     → exit=-1073740940 (0xC0000374 STATUS_HEAP_CORRUPTION)
两列各 600 字节                      → 同样 0xC0000374
```

**影响**：任何查询到 >1KB 的字符串列即越界写（可被利用的堆破坏）。
**建议**：写前按 `len + 需要长度 + 1` 循环扩容；加 2000/20000 字节列回归用例。

#### R-01 JSON 未知字段跳过路径无深度限制（远程 DoS）

已知对象嵌套有 128 层保护（`well_json.c:434`），但**未知字段**走 `jskip_value/jskip_object/jskip_array`（`:205-242`），完全没有 depth 计数。`Json.tryParse` 的"安全"只建立在 `setjmp/longjmp` 上，而栈溢出是 OS 直接杀进程。

复现（C 与语言级双份，语言级 = `File.read` 60KB 恶意 JSON + `Json.tryParse`，与 HTTP body 解析同构）：

```
calling well_json_try_parse...   → exit=0xC00000FD (STATUS_STACK_OVERFLOW)
read bytes 60018                  → exit=0xC00000FD
```

**建议**：`jskip_value` 进入 `++p->depth`（共享 128 上限），超限 `jerr("nesting too deep")`。

#### R-02 MemoryStore 环回读无限递归

`mem_select`（`well_store.c:77`）调 `well_decode`，`well_decode` 的 REF 分支调 `mem_resolve`（`well_serialize.c:263`），后者又调 `mem_select` —— 环上无已访问/深度保护。语言明确允许成环（`tests/cases/40_cycle`），环对象一旦落 Store 再经 Cache 失效回读：

```
stored cyclic A/B under oid 1
cache cleared, reloading from store...  → exit=0xC00000FD
```

**建议**：resolver 维护"解码中 `(type_id,oid)`"集合或深度上限，命中返回 NULL/错误（可先 panic `"cyclic reference on load"` 让问题可见）。
