> 排序原则：正确性 → 语言核心 → 标准库/运行时 → 用户侧存储 → 工程化。

## 0. 当前状态

### 编译器

```text
.we -> C99 -> TinyCC / gcc
lexer / parser / checker / codegen / driver
```

已支持：

- struct / event / enum / controller / handler / func / import；
- if / while / for / of / in / break / continue / return；
- String、Array、Map、Linked；
- oid 写入检查；
- Struct 元数据与行级序列化；
- JSON 解析；
- File / Host API；
- HTTP / WebSocket / MySQL 基础 API；
- 局部作用域释放、覆盖赋值释放。

### 运行时

当前模型：

```text
RC（对象引用计数）
+ oid exec_ref（执行引用租约）
+ oid registry（按 oid 枚举对象）
+ 强制清理（oid 过期且 exec_ref == 0）
+ 固定大小对象池
+ 作用域释放
```

内存关系：

```text
全局 Cache: (type_id, oid) -> 对象
MemoryStore: (type_id, oid) -> 编码字节（纯后端）
Model: Cache / Store 组合转发（当前仍是全局单 Model）
```

## 2. 接下来：语言核心优先

> 多 Model / MysqlStore / FileStore 属于用户侧，已列入暂缓；当前先补语言核心。

### 2.1 P0 继承体系

**controller / handler 方法继承**

- `extends` 当前只被语法接受，没有方法继承；
- 子 controller/handler 应继承父类方法；
- 子类可覆盖；
- 未覆盖时使用父类实现；
- 多级继承；
- 缺失方法错误；
- 验收：父类 `run/onEvent` 可继承，子类可覆盖，现有用例不回归。

**event 继承与子类派发**

- event 继承关系；
- 订阅父 event 是否接收子 event；
- 精确 type_id 派发 vs 层级派发策略；
- 验收：父/子 event 订阅语义明确。

### 2.2 P0 错误处理基础

- `WellError` 分类：参数 / oid / 序列化 / JSON / Store / 连接；
- `Json.parse` 等增加 `tryParse` 或错误码版本，避免只能 panic；
- controller `run`/装配期 panic：
  - 记录错误；
  - 明确退出码；
  - 可选继续启动其他 controller；
- 后续再考虑 try/catch/Result 语法；
- 验收：controller panic 不崩溃进程或给出明确退出码；错误信息带类型/位置。

### 2.3 P1 语法完整性

- `switch/case`；
- enum `fromInt/toString`；
- null 收窄（`T?` 当前仅标注）；
- 容器字面量上下文扩展（函数实参/初始化）；
- 数值类型补齐：char/short/float；
- 验收：每个语法点有 .we 用例；不破坏现有 oid/所有权规则。

### 2.4 P1 invoke

- 同 oid 同步调用；
- 与事件队列/单 runner 的关系；
- 避免死锁/重入规则；
- 验收：same-oid 同步调用顺序确定；异 oid 可并行。

### 2.5 P1 标准库/容器

- Array：✅ `shift/unshift/slice/concat/join/indexOf/includes/clear`；`reverse/sort` 待做；
- Map：✅ `keys/values/clear`；`entries` 待做；
- String：✅ `charAt/byteAt/indexOf/substring/trim/split/contains/startsWith/endsWith`（字节语义）；UTF-8 码点长度待做；
- Bytes：✅ `new Bytes()` + push/get/set/append/appendStr/clear/toString；
- `Json.stringify(obj)`，复用 Struct 元数据；
- Host 增补：文件追加、日志级别、网络客户端；
- 验收：每个方法有 .we 用例；容器 oid/写权限检查保持；RC 无泄漏。

### 2.6 P2 运行时/工程化

- ✅ 调度器 per-worker local deque + work stealing；
- 仍待：抢占/reduction、长 handler 监控；
- 热更新：模块版本/重新加载/旧订阅注销；
- HTTP/WS 生产化：TLS、背压、同端口 Upgrade、pipelining；HTTP 已有多连接 + keep-alive；
- MySQL：TLS、prepared statement、事务 API、caching_sha2；
- 内存池：容器/String 变长 buffer、generation/dead、压力测试；
- 性能：ASan/LSan/fuzz/并发 stress、MSVC/跨平台；
- 泛型/接口/FFI。

## 3. 暂缓：用户侧 Model / Store

以下列入计划，但当前不实现：

| 项 | 状态 | 说明 |
|---|---|---|
| MysqlModel / MysqlStore | ⏸ | 表映射、SQL、业务键、事务 |
| FileModel / FileStore | ⏸ | 文件后端与 mapping |
| MongoModel / MongoStore | ⏸ | 后续 |
| StoreMapping | ⏸ | 字段/列映射、key/oid 列 |
| 业务键 `Model.find` | ⏸ | 依赖 Store 映射设计 |
| 多 Model 共享 Cache | ⏸ | 语言只保证缓存内存语义，归属由用户负责 |

暂缓理由：

- 更偏用户侧/应用层能力；
- 语言核心（继承、错误处理、语法完整性）尚未补齐；
- 当前 MemoryStore + Model + Cache 足够支撑语言测试；
- 避免语言核心与具体数据库绑定。

保留基础：

- `WellStore` 接口；
- MemoryStore 纯后端；
- 全局 Cache；
- Model read-through/write-through；
- TTL / exec_ref / 强制清理。

### 3.1 多 Model / 多 Store 目标（未来）

```text
MysqlModel -> Cache
MysqlModel -> MysqlStore

FileModel -> Cache
FileModel -> FileStore
```

约定：

- `Store.get` / `Store.set` 是纯后端操作；
- 不自动读写 Cache；
- `Model.get`：Cache → Store → Cache；
- Cache 全局共享，key 为 `(type_id, oid)`；
- 不记录来源；
- 多个 Model 可加载同一 key，最后一次 `Cache.set` 覆盖；
- 语言不保证一个 key 只属于一个 Model/Store；
- 数据一致性由用户负责。

### 3.2 MysqlStore Mapping（未来）

- 每个 Store 实例维护 `type_id -> mapping`；
- mapping 包含：
  - table name；
  - business key field -> column；
  - oid field -> column；
  - 字段 -> column；
  - SQL 类型/序列化方式；
- ref 字段存 oid 列；
- 容器字段 v1 用 JSON/TEXT；
- 值必须参数化/转义，不能拼接 SQL；
- mapping 必须在第一次 Store 使用前注册并校验；
- 业务键主键、oid 唯一索引由用户建表负责。

## 4. 关键约定（当前运行时）

### 4.1 oid / IdUtil

- oid 固定 `long`，由 `IdUtil.getId()` 生成；
- serverId + timestamp + sequence；
- `WELL_SERVER_ID` 0..1023；
- 同 oid FIFO、单 runner，异 oid 并行；
- oid 不是 MySQL 主键；业务键才是 DB 主键。

### 4.2 Cache / Model / Store

- Cache 全局共享，key `(type_id, oid)`；
- 不记录对象来源；
- 多个 Model/Store 的 key 冲突由用户负责；
- 当前运行时仍是**单全局 Model + 单 Store**；
- `Model.get` 先查 Cache；miss 时 Store.select → Cache.set；
- `Model.peek` 只查 Cache；
- `Model.set` 先 Store.upsert，再 Cache.set；
- `Model.remove` 先 Store.delete，再 Cache.remove；
- MemoryStore 纯后端，不查 Cache。

### 4.3 GC / TTL / 内存

- RC 保留；对象 rc0 后进入固定大小对象池；
- oid 维护 `exec_ref`：
  - handler/event 持有对象时 +1；
  - 释放时 -1；
- oid 维护 `last_active`：
  - 只由 `Cache.get/set` 更新；
  - 事件执行不延长 TTL；
- oid 过期条件：
  ```text
  TTL 到期
  + exec_ref == 0
  + 调度器空闲
  ```
- 满足后：
  - registry 中该 oid 全部对象强制清理；
  - Cache 行 discard；
  - Store 字节保留；
- 环形数据由 oid 过期兜底；
- 运行时不做环检查；
- 局部作用域释放：
  - loop/block/function/return/break/continue；
- 池：
  - `WELL_POOL_TTL_MS` 到期真正 free；
  - `WELL_POOL_MAX_MB` 上限。

### 4.4 事件 oid

- event `oid` 必须非 0；
- `new Event(0)` / emit 前 oid=0 时，使用 `IdUtil` 自动生成 id；
- 不再有“event.oid=0 立即回调”的特殊语义；
- 所有 event 统一进入 oid 队列调度。

### 4.5 元数据 / 序列化 / JSON

- 每个 struct/event 生成 `WellTypeDesc`；
- 行级二进制格式：`WLS1`；
- JSON 解析：`Json.parse(Type, String)`；
- ref 编码为 `type_id + oid`，解码用 resolver；
- 嵌套容器暂不支持。

### 4.6 网络 / MySQL 限制

- HTTP：多连接 + keep-alive、H1；无 TLS/chunked/pipelining；
- WS：单连接、text frame、独立端口；
- MySQL：native auth、COM_QUERY、无 TLS/prepared/事务 API；
- 最终部署目标 Linux；Windows 使用 TCC 验证。
