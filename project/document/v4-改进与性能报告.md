# WellLangV4 改进与性能报告

日期：2026-10-24  
基线：WellLangV2 `484dff9`（V4 第一个提交 `40b5ca9` 完整导入 V2 工程）  
参照：`document/v3借鉴与v2改进建议.md`（V3 与 V2 是平行版本，V4 以 V2 为基线吸收其中可借鉴项）  
首要目标：**性能**——线程调度、内存分配与回收、运算执行效率；正确性改动先行，任何性能项必须可 A/B 复现。

## 0. 结论摘要

| 方向 | 改动 | 实测（V2 → V4，交替 A/B，中位数） |
|---|---|---|
| 生命周期 journal | 绑定槽位（P0） | 14/14 毒化契约通过（基线仅 2/14） |
| 源码位置 | 每线程位置结构 + 单次 TLS 读 | `well_source_set` 6.5 → 1.5 ns/次 |
| 内存分配 | 非逃逸 struct 全量帧分配（含引用/容器字段） | `bench_alloc` TCC **224 → 72 ns/iter（-67.9%）**、GCC -O2 **98 → 30 ns/iter（-69.4%）** |
| 线程调度 | 唤醒合并 | 4 worker **721k → 829k tasks/s（+14.9%）** |
| 事件派发 | 订阅快照帧内数组 + touch/pin 合并 + 0 订阅者快路径 | **3.24M → 3.64M events/s（+12.3%）** |
| MySQL | 8 KiB 连接读缓冲 | 单连接标量查询 **26 → 22 µs（-15.4%）** |
| LTO | `--release-lto`（opt-in） | `bench_alloc` **91 → 89 ns/iter（-2.2%）** |
| 计算效率 | 无回归（`Host.monoUs` 基准） | loop **+0.2%**、scalar **-1.4%**（TCC，负值=更快） |
| HTTP / WS | 正式 5×7 A/B | HTTP **-1.7%**、WS **+0.1%**（均在噪声内） |
| 回归 | 190 `.we` + 19 C + 14 契约 | 全部通过（MySQL 5.7.40 实库） |

`bench_literals`（字符串字面量查找）保持 14 ns（TCC）/4 ns（GCC）不变，说明改动没有牺牲既有强项。

## 1. P0：绑定槽位 journal（正确性）

V2 的帧 journal 在赋值时按“旧指针地址”扫描条目，地址相等不等于绑定身份。V4 改为：

- `WellCtx` 增加绑定槽位 API：`well_ctx_bind(ctx, slot, owned)` 返回稳定下标，`well_ctx_replace_at(ctx, idx, ...)` O(1) 更新该绑定自己的条目（`runtime/core/wellrt.[ch]`）；
- codegen 为引用局部变量、引用参数、foreach 元素、null 声明建立槽位，并用 `name → slot` 映射随词法作用域保存/恢复（`wellc/codegen.py`）；
- 语义补全：
  - `return <expr>` 统一先求值再释放帧内局部（`return a.value` 不再读已释放对象）；
  - 借用实参经字段/下标/静态字段读取时，在调用期间于 temp journal 上持有一条引用（`f(State.item, resetSource())` 不再悬空）；
  - 引用参数在入口持有一条引用（平凡 `return param` 函数保留快速路径），callee 改写来源容器/静态字段时调用方值仍有效；
  - 赋值/空值/遮蔽/break/continue/early return 路径保持一致。

契约测试 `compiler/tests/contracts/journal_aliases.py` 移植 V3 的毒化方法：对象析构前把字段写成 -999，再验证程序仍输出 42 且最终 live object 为 0。

- 改动前：**2/14 通过**（12 个用例返回 -999，证明提前析构真实存在）；
- 改动后：**14/14 通过**。

性能上，槽位替换消除了每次引用赋值对 journal 的线性扫描；局部变量 journal 的引用计数流量与 V2 相同。

## 2. P1：源码位置（TLS）

生成代码在每个可能 panic 的语句前调用 `well_source_set(file, line)`。V2 每次做两次 `TlsSetValue`。V4：

- Windows（TCC 默认、MinGW gcc）使用 **一个** TLS key 保存每线程 `{file, line}` 结构，写路径为 1 次 TLS 读 + 2 次普通写；
- Linux/ELF 且 GCC/Clang 时使用原生 `__thread`（零成本）；
- 新增 `well_source_file()` / `well_source_line()` 只读接口，供诊断与契约测试使用。

微基准（1 亿次调用，GCC -O2）：两次 `TlsSetValue` **6.5 ns** → 单次 TLS 读 **1.5 ns**。

> 期间实测排除两条“看似正确”的路线：MinGW GCC 16.2 的 `__declspec(thread)` 被静默编译成普通全局变量（无 `.tls` 段，线程间共享），`__thread` 走 emutls 且依赖 `libgcc_s_seh-1.dll`。因此 Windows 上不依赖编译器 TLS。

契约测试 `tests/c/src_pos_tls_test.c`：20 对并发线程 × 8 轮，各自写入唯一 file/line 后读回，`errors=0`。

## 3. P1：MySQL 小包读缓冲

`WellMysqlConn` 内嵌 8 KiB `read_buf`：

- 小请求从缓冲拷贝；
- `n >= 8 KiB` 的请求仍直接 `recv` 到目标 buffer，不额外拷贝、不放大内存；
- 关闭/重连时清空缓冲，保持 EOF/超时语义。

`tools/perf/bench_mysql.we`（单连接、20,000 次 `SELECT 1`，交替 A/B）：**26 → 22 µs/query（-15.4%）**。

## 4. P1：LTO 作为显式配置

- `wellc build/run --release-lto`，或环境变量 `WELL_RELEASE_LTO=1`；
- flags：`-O2 -fwrapv -flto -DWELL_NO_OID_CHECK=1`；
- `--release` 保持原样，便于 A/B；LTO 不默认开启；
- `--release` 的编译器选择改为**真实编译+链接探测**（不再只看 PATH），避免机器上不完整的 gcc 遮蔽可用工具链；Windows 优先 `D:\Soft\gcc\mingw64\bin\gcc.exe`（WinLibs GCC 16.2.0）。

`bench_alloc`：release 91 → release-lto 89 ns/iter（-2.2%）。收益不大但稳定，维持 opt-in。

## 5. P2：非逃逸对象的帧分配（替代 V3 的 chunk region）

V3 的 region 用 16 KiB chunk + size-class 复用 + 私有 RC，只对可证明不逃逸的函数启用；V3 自己也记录了“第一版全量启用导致短调用回归 >3×”。

V2 已经有更强的路径：对**普通标量 struct / 标量数组 / 标量 Map** 直接放 C 帧（零分配）。V4 把这条 fail-closed 证明扩展到：

- 带引用字段（`String`、`Bytes`、struct/event 引用）的 struct；
- 带容器字段（`Array`/`Map`/`Linked`）的 struct；
- 判定不变：对象在声明它的块内只做字段读写，**不传参、不返回、不写入任何容器/静态字段/事件**；
- 新增 `WELL_FLAG_STACK`：生成代码在作用域出口调用该类型的 `destroy_*` 释放字段，`well_obj_free` 对栈存储直接返回；
- 清理点统一由 `emit_scope_release` 发射，覆盖正常退出、`return`、`break`、`continue`；
- 变量名唯一性判定改为“块子树内唯一”，允许两个兄弟循环都用局部名 `o`，并把 foreach 绑定计入声明。

**为什么不引入 chunk region**：对非逃逸对象，帧分配（零 malloc、零 RC、零 registry）严格优于 region（chunk bump + 逐对象析构 + sweep）；能逃逸的对象又不允许被 region 回收。V3 的报告同样说明 region 需要成本模型并会伤害短调用。V4 因此选择“把已有的帧分配证明做宽”，而不是复制 region。doc 中“不要第一版就全量启用”的告警同样适用于此：任何新的可分配类型都必须先通过逃逸证明。

实测 `bench_alloc`（2,000,000 次循环，对象含 `String` 字段）：

- TCC：224 → **72 ns/iter（-67.9%）**
- GCC -O2：98 → **30 ns/iter（-69.4%）**

## 6. 线程调度：唤醒合并

调度器原本在每个入队时，只要有 worker 空闲就 `WakeConditionVariable`；生产者突发时变成每任务一次条件变量系统调用。V4 增加 `g_wake_pending`：

- 已有一次未完成的唤醒时不再重复 signal；
- 被唤醒的 worker 会跨所有本地队列偷取任务，一次唤醒足以消费一批；
- worker 离开 `cond_wait` 后清除标志，后续入队可再唤醒其他空闲 worker；
- worker 处理完一批后若仍有积压，沿用既有 `sched_notify()` 继续唤醒。

`bench_sched`（300k tasks / 64 oids / 4 workers，交替 7 轮去掉 2 轮预热）：**720,973 → 828,616 tasks/s（+14.9%）**。

## 7. P3：测试与基准方法

- `tools/perf/ab.py`：通用交替 A/B 运行器——每个变体跑 N 个独立进程，逐轮轮换启动顺序，丢弃预热轮，输出 min/median/max 与原始 JSON；
- `tools/perf/bench_mysql.we`：单连接标量查询基准；
- `tests/contracts/journal_aliases.py`：14 个 journal 毒化契约（P0）；
- `tests/c/src_pos_tls_test.c`：20 对线程的源码位置隔离契约；
- C 测试统一追加 `-UNDEBUG`，避免 `-O2` 下 `assert` 被编译掉；
- 所有 A/B 均保留旧二进制（V2 基线由 `git archive 40b5ca9` 导出到 `project/tool_ai/baseline/`），同机交替运行。

## 9. 第二批性能项（2026-10-24）

### 9.1 高分辨率计时与抗优化基准

`Host.nowMs()` 走 `GetSystemTimeAsFileTime`，Windows 默认 10–15 ms tick；且 GCC -O2 会把
`acc = acc + i` 这样的循环闭式化简（`loop_w.we` 曾因此直接 `ms=0`）。V4 新增：

- `well_mono_us()`（QPC / `clock_gettime(CLOCK_MONOTONIC)`）与语言内建 `Host.monoUs(): long`；
- `tools/perf/bench_loop.we`、`bench_scalar.we`：累加器反馈进 addend，避免闭式消除；微秒计时；
- 用例 `195_mono_us` 校验单调性。

交替 A/B（V2 基线打上同一时钟补丁，保证同一程序）：

| 基准 | TCC | GCC -O2 |
|---|---|---|
| loop `ns_per_iter` | +0.2% | -0.3% |
| scalar `ns_per_op` | -1.4% | -0.9% |

即 journal/返回求值等代码生成改动没有引入计算回归。

### 9.2 事件派发订阅快照

`dispatch_event` 原来每个事件 `realloc`+`free` 一次订阅者快照；改为 8 槽帧内数组，超过才分配。
基准 `bench_event.c` 先填满队列再启动 worker 排空（避免把生产者/消费者锁竞争误当成派发成本）：

- 3,241,922 → 3,583,292 events/s（**+10.5%**，300k events × 2 订阅者，7 轮交替）。

随后合并了每个事件都做的两次活动表加锁（`well_model_touch_oid` + `well_oid_pin` →
`well_oid_touch_and_pin` 一次加锁），并让 0 订阅者的事件直接返回（不再 pin/touch）：

- 3,516,240 → 3,640,074 events/s（**+3.5%**）；
- 相对 V2 基线合计 **3.24M → 3.64M events/s（+12.3%）**。

### 9.3 HTTP / WS 正式 5×7 A/B

`tools/perf/formal_ab.py`：每个变体 5 个独立进程 × 7 轮、前 2 轮预热、进程间轮换 A/B；
TCC `-run`、4 workers、8 客户端、3 秒/轮。结果：

| 场景 | V2 中位 rps | V4 中位 rps | 差异 | p50/p99（V2 → V4） |
|---|---|---|---|---|
| HTTP keep-alive `/bench` | 206,281 | 202,749 | **-1.7%** | 21.7/63.3 → 22.4/64.8 µs |
| WebSocket echo | 198,110 | 198,330 | **+0.1%** | 23.0/60.2 → 23.0/62.4 µs |

两项都在进程间噪声内（V2 HTTP 单进程 min 165k / max 211k）。结论：V4 的收益集中在
分配/调度/事件微路径，HTTP/WS 的 handler 内联路径没有可感知变化，也没有回归。

`--release`（GCC -O2）下用同一流程再跑一轮：

| 场景 | V2 中位 rps | V4 中位 rps | 差异 | p50/p99（V2 → V4） |
|---|---|---|---|---|
| HTTP keep-alive | 218,730 | 219,552 | **+0.4%** | 21.1/56.6 → 21.0/56.6 µs |
| WebSocket echo | 203,940 | 204,130 | **+0.1%** | 22.7/54.8 → 21.9/58.0 µs |

`--release` 对两个版本都带来约 6–8% 的 HTTP 吞吐提升（219k vs TCC 203k），V4 与 V2 的相对
差距仍在一两个百分点内。

### 9.4 per-oid arena：实测不具收益，已回退

按 `per-oid-arena-实施方案.md` 做了一个默认关闭的 `WELL_ARENA=1` 原型（bump chunk +
组内 live 计数 + 最后一对象释放整链），并用 `bench_arena.c` 测“每轮 64 个同 oid 对象全部释放”：

| 分配路径 | ns/object（GCC -O2，20k 轮 × 64 对象） |
|---|---|
| 现有 size-class 池（`WELL_ARENA=0`） | **24.8** |
| per-oid arena（`WELL_ARENA=1`） | 34.7 |

原因很明确：V2 的池已经有**每线程无锁缓存**，而 arena 的 bump 需要跨线程同步（每对象两次
shard 自旋锁）加每轮 chunk `malloc/free`；只有在“整组对象由 TTL 批量回收”且对象数量很大时，
组释放才可能抵消分配端的同步成本。该原型契约测试（对齐/组释放/上限 fallback/oid0/String）
全部通过，但按“无稳定收益则回退”的规则**未纳入默认路径**，代码与基准留在
`project/tool_ai/arena-experiment/` 供后续 TLAB 版本参考。

## 10. 未采纳 / 后续

- 未采纳 V3 的普通 `retain/release`（`atomic_load + atomic_inc/dec`），V2/V4 的单次 RMW 更省；
- 未采纳 V3 数组实现，保留 V2 内联 4 元素；
- 未默认开启 LTO / region；
- per-oid arena 实测不具收益（§9.4），若要做需先实现 per-thread TLAB（失败才回到本原型）；
- 后续可做：容器/字符串逃逸场景的 region 化、事件派发 1/N 订阅者的分档快路径、
  `--release-lto` 下的 HTTP/WS 5×7。

## 11. 跨语言报告驱动的优化（2026-10-26）

依据 `E:\Work\WellTest\REPORT.md`（2026-10-24）中 v4 的短板（算术 1.42× C、分配 1.58× C），
在“只保留语法相同、同 oid 串行、异 oid 并行”的约束下做了三项优化：内联除零检查、内联
oid 写检查（panic 位置随调用携带）、单线程阶段普通 RC。同一 harness 复测：

| 维度 | 报告值 | 复测值 | 变化 |
|---|---:|---:|---:|
| 数组访问 | 0.921 ns | 0.919 ns | ≈0 |
| 标量算术 | 6.300 ns | **4.253 ns** | -32.5% |
| 短生命周期分配 | 47.376 ns | **26.497 ns** | -44.1% |
| HTTP | 207,731 req/s | 212,843 req/s | 单次测量，含环境漂移 |
| WebSocket | 206,048 msg/s | 215,483 msg/s | 同上 |
| MySQL | 24.9 µs | **24.3 µs** | -2.4% |

> 网络基准的绝对值会随机器后台负载漂移（同一份代码同日 192k–213k rps）。第二轮逐请求
> 全局锁削减（IdUtil 块分配、连接内请求复用、路由事件免注册）用同会话交替 A/B 测得
> **HTTP +4.5%**（192,470 → 201,176 rps，p50 22.4→21.6 µs）、WS +0.2%（噪声内）。

约束放宽点与差异见 [`v4-性能优化-放宽约束说明.md`](v4-性能优化-放宽约束说明.md)；原始 JSON 在
`E:\Work\WellTest\tool_ai\results\v4_opt_final.json` 等文件。
