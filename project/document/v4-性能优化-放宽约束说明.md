## 2. 本次改动

### 2.1 除零/取模检查内联（标量算术）

`/`、`%` 的变量除数原来调用跨编译单元的 `well_int_div` / `well_int_mod`，函数调用阻止了常量传播、
寄存器分配与强度削减。改为 `wellrt.h` 中的 `static inline` 版本：

```c
static inline long long well_div_checked(long long a, long long b) {
    if (WELL_UNLIKELY(b == 0)) return well_int_div(a, b); /* panic */
    if (WELL_UNLIKELY(a == (-9223372036854775807LL - 1) && b == -1)) return 0;
    return a / b;
}
```

- 语义不变：零除数仍 panic；`INT64_MIN / -1`、`INT64_MIN % -1` 仍返回 0；
- 常量非零除数仍由 codegen 直接发原生 C 运算（`emit-c` 里可看到 `% 1024` 被折叠）；
- 仅变量除数走内联检查。

### 2.2 oid 写检查内联（对象分配 / HTTP / WS）

字段写原来对每个字段调用一次 `well_check_oid()`（跨 TU 函数调用），且语句前还要发一次
`well_source_set()`。改为：

```c
well_check_oid_at((void*)_t, ctx, "field write", "file.we", 27);
```

宏内联 oid/frozen 比较，只有违规时才调用 `well_check_oid_fail(...)`，并在那里设置语句的
file:line 后 panic。因此：

- panic 文本与位置**不变**（位置由 `check_at` 参数精确携带）；
- 字段写语句不再需要前置 `well_source_set`（`gen_stmt` 通过 `_self_sourced_panic` 识别）；
- 其它可能 panic 的语句（数组/Map 写入、调用、除法等）仍保留 `well_source_set`。

### 2.3 单线程阶段使用普通 RC（唯一的原子性放宽）

`well_retain` / `well_release` 原来对所有对象做原子 RMW。现在：

- 进程启动到**第一个线程创建之前**（装配期 + `controller.run()`，单线程）使用普通
  `rc++/rc--`；`g_rc_single` 标志在 `well_thread_start()` 里、任何线程真正启动之前清零，
  之后全部恢复原子操作；
- 依据：此阶段不存在并发访问（语言层没有线程 API；HTTP/WS/Timer/调度器的线程都经由
  `well_thread_start` 创建），创建线程的系统调用本身提供内存屏障，切换前的计数对后续线程可见；
- 可观测语义不变：RC 数值、析构时机、oid/事件/TTL 行为都一致，变化的只是"何时需要原子指令"。

### 2.4 逐请求全局锁削减（HTTP / IdUtil）

HTTP inline 路径每请求原来会碰 3 个全局同步点：请求结构池 `g_http_lock`（alloc/free 各一次）、
IdUtil 的 `g_id_lock`、路由事件的 registry 分片锁（add/remove）。第二轮：

1. **IdUtil 块分配**：线程在锁内一次预取当前毫秒的 64 个序号，其余在 TLS 缓存里发放；
   锁频率降到 1/64。`(timestamp, sequence)` 仍由全局分配器唯一发放，单线程内递增。
2. **连接内请求结构复用**：每个连接线程保留一个 `WellHttpRequest`，inline 响应路径不再进出全局
   请求池；只有异步/未响应请求仍走全局 list/map。
3. **路由事件免注册**：`http_route_N` 改用 `well_new_zero_unregistered`（事件创建后在同线程
   同步释放，没人能按 oid 查到它）；若 handler 把它交给 `Model.set`，`well_register_obj`
   仍会正常注册。

### 2.5 差异（第二轮）

| 项 | 优化前 | 优化后 | 影响 |
|---|---|---|---|
| Id 序号 | 每次全局锁内递增 | 每线程一次预取 64 个序号 | 跨线程不再严格全局递增；唯一性、可排序性、单线程递增不变 |
| 路由事件 | 创建即注册 | 创建时不注册，`Model.set` 时注册 | TTL 不枚举未被 Model 持有的事件（与普通 struct 相同） |
| 请求结构 | 全局池 + 锁 | 连接线程复用 | 仅 inline 同步路径；异步请求路径不变 |

## 3. 与优化前的差异（需知悉）

| 项 | 优化前 | 优化后 | 影响 |
|---|---|---|---|
| RC 原子性 | 全程原子 | 单线程阶段普通计数，首个线程创建时切换 | 仅性能；若有绕过 `well_thread_start` 自行创建的线程并在切换前访问对象，需要先手动触发切换（当前语言/运行时不会发生） |
| oid 检查位置 | 独立函数 + 语句前 TLS 位置 | 内联 fast path，`check_at` 携带位置 | panic 文本/位置不变 |
| 除零检查 | 跨 TU 调用 | 头文件内联 | panic 文本/位置不变 |
| IdUtil 序号 | 全局严格递增 | 每线程按块领取 | 唯一性不变；跨线程顺序弱化 |
| 语法 / oid 执行模型 | — | **不变** | 三条约束均满足 |

没有删除 oid 检查、没有改动 TTL/事件 pin/journal 语义，也没有改变 panic 输出格式。

### 4.2 路由事件帧分配（HTTP / WS）

路由包装器原先每请求/每条 WS 消息都在堆上分配事件对象，并 `well_retain` 4 个请求/消息字符串。
新增 fail-closed 逃逸检查 `_stack_event_ok(handler)`：仅当 handler

- 只以 `e.field` 形式读取事件参数（不把 `e` 本身传参、赋值、存入容器/Model），且
- 不写事件参数字段（避免借用字段被错误 release），且
- 事件类型没有字段默认值（WS；HTTP 路由事件原本就不套构造函数）

时，包装器在 **C 帧**构造事件：`memset` + 填 `hdr` + 字段直接借用（不 retain），handler 返回后
无需释放。其它 handler 保持原堆路径（HTTP 侧仍用 unregistered 分配）。

同会话交替 A/B（对照 `47b0e7b`，5 进程 × 7 轮）：

| 场景（12 workers / 8 clients） | 优化前 | 优化后 | 变化 |
|---|---:|---:|---:|
| HTTP keep-alive | 204,072 rps，p50 21.4 µs，p99 56.5 µs | **205,605 rps，p50 21.3 µs，p99 54.7 µs** | **+0.8%** |
| WebSocket 回显 | 187,674 msg/s | **190,988 msg/s** | **+1.8%** |

32 客户端下也做过一次对照（3 进程 × 5 轮）：中位数在噪声内（−3.2%），但 p50/p99 略好；
该配置下 32 个 Python 客户端进程会和 12 个 worker 抢 6 核 CPU，不适合作为判据。

原始数据：`ab_http_stackevt.json`、`ab_ws_stackevt.json`、`ab_http_32c.json`。

### 4.3 release（zig cc / clang -O2）模式与同会话 C 对比

报告里的 Well 后端使用 `zig cc -O2 -fwrapv`（clang 20）构建，前面的 TCC 数据只代表默认构建。
用同一套 `formal_ab.py --release`（WELL_CC=`zig cc`，WELL_CFLAGS=`-O2 -fwrapv`）复测：

| 场景（12 workers / 8 clients，release） | `4442162` | 当前 | 变化 |
|---|---:|---:|---:|
| HTTP keep-alive | 208,700 rps，p50 21.1 µs | **210,820 rps，p50 20.6 µs** | **+1.0%** |

同会话把 C 参考实现拉进来对比（`run_http.py --langs well_v4,c`）：

| 实现 | rps | p50 | p99 | RSS |
|---|---:|---:|---:|---:|
| C（zig cc -O2） | 228,667 | 20.1 µs | 50.9 µs | 5.2 MB |
| V4（release） | 208,410 | 21.3 µs | 57.9 µs | 6.2 MB |

即 V4 约为 C 的 **91%**。差距的主要来源不是某条慢语句：C 参考服务器**只做**
“`recv` → 找 `\r\n\r\n` → 发送常量响应”，而 V4 每请求还要做完整的 HTTP 解析、请求结构、
snowflake id、路由匹配、事件构造与 handler 派发。要再接近 C，需要改 IO 模型（IOCP）或为
“无 body/固定响应”的场景做专门的旁路，属于下一步的结构性工作，而不是继续微调。

原始数据：`ab_http_release_444.json`；C 对比在 `E:\Work\WellTest\tool_ai\results\http_vs_c_now.json`。
