# Well v1 → v2 性能对比（2026-10-23 第一批）

> 基线：`E:\Work\WellLang`（v1，提交 `ccbe633`）
> 优化：`E:\Work\WellLangV2`（v2，提交 `a083e07` + 对象头 48B 重排）
> 口径：同机、同工具链、同负载交替测量；数据用于**相对比较**，不是跨机绝对值。

## 1. 环境与方法

| 项 | 值 |
|---|---|
| CPU | Intel Core i5-12400F（6C/12T，2.5GHz） |
| OS | Windows 11 专业版 10.0.26200 |
| C 编译器 | 仓库内 TinyCC 0.9.27（Windows 默认工具链） |
| Python | 3.12.14（benchmark 客户端进程） |
| HTTP/WS 服务端 | `tcc ... -run` 在 tcc.exe 进程内编译并执行（见 §5 说明） |
| 客户端 | Python **多进程**（每进程一条 keep-alive 连接），避免 GIL 限制 |
| 采样 | 每配置 2–5 轮，报告吞吐中位数/最优值；p50/p99 取最优轮 |
| 测试 | `WELL_WORKERS=1`，MySQL 5.7.40 本地实例（独立 data 目录，端口 3306） |

复现命令（在 `project/compiler` 下）：

```powershell

# HTTP → MySQL：每请求执行 SELECT 1 AS x（8 连接池）
python tools/perf/bench_http.py --source tools/perf/mysql_server.we --path /db `
    --label v2 --workers 1 --clients 8 --seconds 2 --repeat 3

# 对比 v1：在命令前设置
$env:BENCH_COMPILER = "E:\Work\WellLang\project\compiler"
```

> 说明：v1 的 String 直接走 malloc/free；v2 把 String 放入 size-class 池，并用
> **线程本地池缓存**（`WELL_POOL_TLS=0` 可关闭）消除每次分配/释放的全局池锁。
> 单线程微基准因此从“略慢”转为持平/更快；关掉 TLS 缓存时对象分配会回到
> +3%~+6% 的锁开销。

5 小时跑到 **51.9 亿请求**、288k req/s、0 错误；RSS 启动 13.72MB，峰值 14.49MB，

响应缓冲均已达到稳态。8h 与 100MB/s churn：churn 已通过（4.56GB/s），8h 留给
无人值守环境。

## 3. 本批改动

提交：

- `451d2f0 perf(runtime): O(1) string-literal intern table, fast String pool, inline HTTP/WS handler paths`
- `a083e07 perf(http/ws): enable inline handler dispatch by default; shrink object header; cache request paths`

关键改动：

1. **字符串字面量 O(1) 查找**（`wellrt.c`）
   - 原实现每次求值字面量都线性 `strcmp` 整张驻留表（O(字面量数)）。
   - 新增发布式开放寻址哈希索引（与 items 快照一起原子发布），读路径无锁。
   - 65 个字面量时 448 → 113 ns；字面量越多收益越大。

2. **HTTP 处理器内联执行**（`well_http.c`，默认开启，`WELL_HTTP_INLINE=0` 回退）
   - 每个 HTTP 请求本来就有全新 oid，不存在同 oid FIFO 冲突；把 handler 直接放在
     连接线程执行，去掉“reader → 调度器 worker → reader”的两次上下文切换、
     任务队列/节点池/条件变量唤醒。
   - 保留与 worker 相同的 panic 隔离边界（setjmp/longjmp）。
   - 端到端 77.5k → 203k req/s；RSS 下降。

3. **WebSocket 处理器内联执行**（`well_ws.c`，默认开启，`WELL_WS_INLINE=0` 回退）
   - 每条连接的消息本来就在该连接的 reader 线程串行处理，内联不改变顺序语义；
     去掉每帧一次任务/队列/唤醒。
   - 回显 82.5k → 165k msg/s。

4. **HTTP 响应快速路径**（`well_http.c`）
   - 去掉每请求 `snprintf`；200/`ok`/keep-alive 使用预构造响应一次 `send`；
     通用路径手写状态行/长度/连接头。单请求约 +7% 吞吐。

5. **keep-alive 路径 String 缓存**（`well_http.c`）
   - 同一连接重复访问同一 path 时复用已驻留的 `String`，去掉每请求一次分配+哈希。

6. **对象头 56B → 48B**（`wellrt.h`）
   - 8 字节字段前置、4 字节头字段后置，消除对齐填充；`alloc_size` 改 32 位。
   - `WellObj` 48B、`WellString`/`WellBytes` 72B；短字符串的池 class 下降一档。

7. **String 池化 + 线程本地池缓存**（`wellrt.c`）
   - String 块进入统一 size-class 池；修复了“池未命中时 malloc 尺寸未按 class 对齐，
     释放时被当作更大 class 复用”的堆越界隐患（该 bug 曾导致并发 HTTP 偶发
     0xC0000005）。
   - 每个线程保留有界（32/class、256KB）的空闲块缓存，分配/释放不再每次抢全局池锁；
     线程退出时归还全局池。TLS key 在 `well_init()` 单线程阶段创建，避免两个连接
     线程并发创建 key 后共享同一缓存。`WELL_POOL_TLS=0` 可关闭做 A/B。

8. **JSON 缓冲复用**（`well_json.c`）
   - 每个 JSON 字符串原来要 malloc 一个临时缓冲、再复制进 String、再 free；
     现在整个 parse 复用一个可增长缓冲，字符串值只做一次最终拷贝。
     150B 对象解析 2173 → 1863 ns（-14%），键/字段名不再逐次分配。
   - `Json.stringify` 的小输出（≤512B）在栈上构建，超出才 malloc；150B 对象
     stringify 996 → ~990 ns（噪声内），少一次 malloc/free。

9. **调度器空闲唤醒抑制 + 同 oid 批量出队**（`well_event.c`）
   - 记录阻塞在条件变量上的 worker 数，入队只在确有空闲 worker 时 `signal`；
     满载时不再为每个 task 做一次无效唤醒。
   - 每次调度锁内取同 oid 最多 32 个节点，按 FIFO 顺序依次执行，完成后一次
     归还节点池；把每 task 两次加锁降为约两次/32 task。
   - 单 oid task 吞吐 W=1 1.005M→1.192M/s（+19%）；64 oid W=4 614k→650k/s。
     W=4 仍受全局调度锁与 trivial task 限制，下一步 per-worker 队列/锁。

10. **MySQL 连接池按空闲时间 Ping**（`well_mysql.c`）
    - 原先每次从池里借连接都发 `COM_PING`，一个简单查询变成两次往返；
      现在只对空闲超过 `WELL_MYSQL_PING_IDLE_MS`（默认 1000ms）的连接 ping，
      刚用过的连接直接复用。`0` = 每次 ping，`<0` = 从不 ping。
    - HTTP→MySQL 65.7k → 89.7k req/s（+37%）；p50 67 → 49 µs。

11. **WebSocket 帧缓冲复用**（`well_ws.c`）
    - 每条连接保留一个可增长的收帧缓冲，不再每帧 malloc/free；文本/关闭帧
      解析后立即复制进 String，缓冲可安全复用。吞吐在客户端噪声内持平
      （161–167k msg/s），RSS 13.7–13.8MB。

12. **size-class 改为 8B 对齐**（`wellrt.c`）
    - `POOL_ALIGN` 16→8：String/event 块按精确大小分配（当前 64B/88B），不再向上
      取整到 16B class；所有 Well 对象只含 8B 对齐字段。
    - HTTP p50 23.3→21.6 µs，8 客户端 203→204k req/s；对象 new+release 83→81 ns。

13. **String 去掉 `data` 指针**（`wellrt.h`）
    - String 字节一直内联在 header 之后（所有分配点都是 `s+1`），指针字段纯冗余；
      改为 `well_str_data(s) = (char *)(s + 1)` 访问器。`WellString` 72→64B。
    - String 8B new+release 91.9→81.7 ns（-11%）；JSON stringify 990→950 ns（-4%）；
      HTTP 吞吐在噪声内持平（204k）。

14. **String hash 惰性计算**（`wellrt.c`）
    - 创建 String 时不再计算 FNV-1a；只有作为 Map key 或参与相等比较时才由
      `well_string_hash()` 计算并置 `WELL_FLAG_HASHED`。字面量仍在驻留时算一次。
    - `String.fromInt` 101.7→88.8 ns（-13%）；JSON parse 1863→1800 ns（-3%），
      150B 对象 stringify 950→840 ns（-12%）。Map/相等比较语义不变。

15. **JSON 无转义字符串快速路径**（`well_json.c`）
    - 先扫描到闭合引号；不含反斜杠/控制字符时整段 `memcpy`，不再逐字符
      `jstr_push`。含转义的字符串回退到原解码器。150B 对象 parse 1800→1775 ns。

16. **WS/MySQL 每消息/每查询分配清理**
    - WS text 帧用已知 `plen` 构造 String（`well_string_new_n`）：省一次 strlen，
      并保留内嵌 NUL（旧 `well_string_new` 会在 NUL 处截断）。
    - MySQL 查询包 ≤256B 使用栈缓冲，避免每查询一次 malloc/free；结果 String
      使用已知长度。端到端吞吐在噪声内持平，主要减少分配抖动。

17. **HTTP/WS listen backlog 16 → 128**
    - 大量短连接/突发 connect 时给 listener 更大的排队余量；keep-alive 吞吐不变。
      这是并发健壮性调整，没有可测的单请求收益。

18. **live 对象计数默认关闭**（`wellrt.c`）
    - `g_live` 只在 `WELL_RC_DEBUG=1` 时做原子更新；普通运行不再为每次对象
      分配/释放付两次全局 atomic RMW。
    - 对象 new+release 81.2→68.8 ns，String 8B 82.4→58.3 ns，alloc 循环
      376→353 ns，JSON parse 1775→1706 ns。HTTP/WS/MySQL 端到端小幅改善。
    - C 测试 runner 自动设置 `WELL_RC_DEBUG=1`，`well_live_count`/泄漏断言语义不变。

19. **字符串字面量按调用点缓存**（codegen + `well_string_lit_slot`）
    - 生成 C 从每次 `well_string_lit("x")`（哈希 + 探表）改为
      `({ static WellString *s; well_string_lit_slot(&s, "x"); })`：命中时一次
      指针加载 + 分支。字面量求值 113→96 ns（vs v1 4.7×）。
    - 多线程首次填充写的是同一个驻留指针，属于良性竞态。

20. **String 释放跳过 oid registry**（`wellrt.c`）
    - String 从不在 oid registry 里、也没有 event payload pin；释放时不再做
      `well_registry_remove` 的分片自旋锁。String 8B new+release 58.3→49.0 ns，
      `String.fromInt` 82.2→69.1 ns，JSON stringify 853→820 ns。

21. **作用域退出快路径**（`wellrt.h` + codegen）
    - `well_ctx_mark` 改为 header inline；生成 C 用 `well_ctx_release_to(ctx, mark)`，
      当 `ctx->n == mark`（作用域没有 own 引用）时直接跳过 out-of-line 调用。
    - alloc 循环 353→338 ns（vs v1 -20%），字面量循环 96→94 ns。

22. **只在可能 panic 的语句更新源码位置**（codegen）
    - 旧生成码在每条语句、每次 while/for 条件前都调用 `well_source_set`（两次 TLS 写），
      纯算术/局部赋值/循环条件也付这个成本。
    - 新增 `expr_may_panic/stmt_may_panic`：仅 Call/New/除法取模/字段或容器写等
      可能 panic 的语句发射 source；panic 定位用例 99/101/141 等全部通过。
    - 字面量循环 94→48 ns（vs v1 9.3×），alloc 循环 338→320 ns（vs v1 -24.5%）；
      HTTP 205.8–206.5k、WS 167.5k msg/s（小幅提升）。

23. **temp journal mark 按需启用**（codegen）
    - 每个语言作用域原先无条件 `int tm = well_temp_mark()` + 退出
      `well_temp_release_to(tm)`，即使作用域里没有任何 owned 临时值（纯字面量/
      算术/循环计数）。两次 TLS 访问落在每个循环迭代上。
    - 现在先发 `int tm = 0;`，只有作用域内真的发射了 `well_temp_hold` 才升级为
      `well_temp_mark()` 并生成 release；`break/continue` 的清理仍用 0 兜底。
    - 字面量循环 48→17 ns（vs v1 26×），alloc 循环 320→273 ns（vs v1 -35.6%）。

24. **JSON stringify 分块转义 + 手写整数输出**（`well_json.c`）
    - `jo_escaped` 不再逐字符 `jo_putc`：扫描到转义字符前整段 `memcpy`；
    - `jo_long` 去掉 `snprintf`，改手写十进制。
    - stringify 820→590 ns（vs v1 996，-41%）；parse 1706→1620 ns（-25% vs v1）。

25. **WebSocket 连接启用 TCP_NODELAY**
    - 与 HTTP 对齐，accepted socket 设置 `TCP_NODELAY`。回显基准（请求-响应，
      没有未确认数据）在噪声内持平 159–167k msg/s；避免服务端推送/流式场景被
      Nagle 合并延迟。

26. **WebSocket 帧头 mask+payload 合并读取**（`well_ws.c`）
    - 旧路径每帧最多 4 次 `recv`：2 字节头、扩展长度、4 字节 mask、payload。
    - 现在头部之后一次 `recv` 读入 `[mask][payload]`，在 frame_buf 内原地解掩码；
      小帧从 4 次 syscall 降到 2 次。回显 164.6k→**173.0k msg/s（+5%）**，
      p50 25–27→**24–25.8 µs**。

27. **WebSocket 小帧 header+payload 合并发送**（`well_ws.c`）
    - 旧路径每帧两次 `send`（header、payload）；≤1KB 的帧改为栈上拼成一块再
      `send_all`，写锁已保证不会与其他帧交错。回显 173.0k→**176.9k msg/s**，
      p50 24.0–24.5 µs；配合上一项的 2 次 recv，每帧共 2 recv + 1 send。

28. **MySQL 小查询包 header+payload 合并发送**（`well_mysql.c`）
    - `my_write_packet` 旧路径固定两次 `send`（4B 头 + payload）；≤512B 的包改为
      栈上拼接后一次发送。HTTP→MySQL 89–91k req/s，与基线 88.6–90.5k 基本持平
      （DB 占比高），每次查询少一次 syscall。

29. **WebSocket 读侧按连接缓冲**（`well_ws.c`）
    - 新增 `ws_buf_fill`：一次 `recv` 读入整帧（或连续多帧），从缓冲区解析
      header/mask/payload；典型小帧从 2 次 recv 降到 1 次，且多帧可复用同一次读。
      缓冲区按需增长，空闲连接不分配。回显 176.9k→**190.0k msg/s（+7%）**，
      p50 23.1–25.0 µs。

30. **String.fromInt 两位数表**（`wellrt.c`）
    - 每轮 `u / 100` 一次除法生成两位数字（原实现每位一次 `/10`），
      `String.fromInt` 69.1→**55.6 ns**（vs v1 -61%）。负数/LLONG_MIN 路径未变。

31. **JSON 整数输出两位数表**（`well_json.c`）
    - `jo_long` 与 `String.fromInt` 使用同一套两位表，stringify 590→**583 ns**
      （150B 对象，3 个整数）。

32. **HTTP pipelined 响应批量发送**（`well_http.c`）
    - 连接增加 `outbuf`；inline 响应先格式化进缓冲，读到 scratch 里还有完整
      下一个请求时继续处理，没有才一次性 `send`。`Http.stop()` 在 handler 内
      调用时先 flush 当前连接。
    - depth 8/16/32：815k / 929k / **953k req/s**；v1 depth32 88.3k，**+979%**。
      逐请求 depth1 保持 211k。

33. **HTTP pipelined 混排响应顺序修复**（`well_http.c`）
    - route 响应在 `outbuf` 中时，404/405/async 的直接 `send` 会抢先；现在 direct
      send 前先 flush `outbuf`。`test_http_mixed.py` 验证 `/bench,/nope,/bench`
      返回 `[200,404,200]`。

## 5. 环境限制（Device Guard / Smart App Control）

本机 Smart App Control 处于启用状态（`VerifiedAndReputablePolicyState=1`）。会话中途
开始拦截**新链接的未签名 exe**（`WinError 4551` / “blocked by your organization's
Device Guard policy”），包括 `wellc` 刚生成的测试 exe 和新下载的 GCC。此前已存在的
TinyCC 不受影响。

因此本批数据采用：

- `tcc ... -run` 在 `tcc.exe` 内编译并执行生成的 C（同一 TCC 代码生成器，无 exe 落地）；
- Python 多进程压测客户端；
- 这不是产品代码改动，只是本机测量/回归的执行方式。CI（Linux gcc）与普通开发机
  仍按原生 exe 路径运行。
