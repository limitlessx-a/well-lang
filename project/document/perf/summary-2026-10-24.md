### 1.3 CPU 调度：多生产者（4 producer、300k task、2000 循环）

| worker 数 | task/s | 相对 W1 |
|---|---|---|
| W1 | 767,263 | 1.00× |
| W2 | 1,376,146 | 1.79× |
| W4 | **2,083,333** | **2.72×** |

单生产者 `bench_sched.c` 的 W4 只有 1.83×，是**生产者线程自己成为瓶颈**；
4 个生产者并行入队时 W4 达到 2.72×。当前“全局 qmap 锁 + 每 worker ready 队列”
已能让生产/消费并行；per-worker 分片锁的优先级可下调。

原始输出：`bench_sched_multi.c`（`WELL_WORKERS=1/2/4`）。

8 producer 时：W1 716k、W4 1.48M、W8 2.19M。**W4 反而低于 4 producer 的 2.26M**，
说明 8 个并发生产者开始被全局 qmap 锁串行化；W8 靠更多消费者吸收。高并发
producer 场景才是 per-worker 分片锁的主要收益点。

## 5. 关键优化（按收益排序）

1. 字面量按调用点缓存（17ns；26×）。
2. 按 panic 可能过滤 `well_source_set` + temp journal 按需 mark（循环 94→17ns）。
3. live 对象计数默认关闭（对象/字符串分配释放显著下降）。
4. String 释放跳过 oid registry；64B String / 48B Object。
5. HTTP/WS inline handler + 响应快速路径。
6. WS 读缓冲（1 recv）+ 小帧合并发送（1 send）；MySQL 小包合并发送。
7. JSON 分块转义 + 手写整数输出（stringify -41%）。
