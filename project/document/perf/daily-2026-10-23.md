## 关键改动

1. **字符串字面量哈希索引**：每次字面量求值不再线性 `strcmp` 整张表；发布式
   快照 + 开放寻址，读路径无锁。
2. **HTTP handler 内联**（默认）：请求 oid 唯一，连接线程直接执行 handler，
   省去两次线程 handoff；保留 setjmp panic 隔离。`WELL_HTTP_INLINE=0` 可回退。
3. **WS handler 内联**（默认）：每连接消息本就串行，reader 线程直接执行；
   `WELL_WS_INLINE=0` 回退。
4. **HTTP 响应快速路径**：去掉每请求 `snprintf`，200/`ok`/keep-alive 预构造
   响应一次 send。
5. **路径 String 缓存**：keep-alive 同路径复用驻留 String。
6. **对象头 48B**：8 字节字段前置消除 padding；`alloc_size` 32 位。
7. **String 池化 + 堆越界修复**：String 块按 class 对齐分配，修复并发 HTTP
   偶发 0xC0000005（未对齐 malloc 块被当作更大 class 复用）。
8. **线程本地池缓存**：对象/String 的分配/释放先走本线程有界空闲链（32/class、
   256KB），消除全局池锁；对象 new+release 101→83ns、alloc/free 62→43ns。
   `WELL_POOL_TLS=0` 可回退对比。
9. **JSON 解析缓冲复用**：整个 parse 复用一个可增长字符串缓冲，150B 对象解析
   2173→1863ns（-14%）。
10. **调度器空闲唤醒抑制 + 同 oid 批量出队**：只在有空闲 worker 时 signal；
    一次锁内取最多 32 个同 oid 节点。单 oid task 吞吐 W=1 1.005M→1.192M/s
    （+19%），64 oid W=4 650k/s（仍受全局调度锁限制）。
11. **MySQL 池 PING 按空闲时间**：默认只对空闲 >1s 的连接 ping，简单查询少一次
   往返；HTTP→MySQL 65.7k→89.7k req/s（+37%）。
12. **内存长稳（60s / 300s / 600s / 1800s / 3600s）**：60s/8 连接 1300 万请求、
    215k req/s；300s/12 连接 8656 万请求、286k req/s；600s/12 连接 1.73 亿请求、
    286k req/s（最新一轮稳态斜率 -2.10MB/h）；1800s/12 连接 5.22 亿请求、
    288k req/s（最新斜率 -0.90MB/h）；**3600s/12 连接 10.4 亿请求、287k req/s、
    0 错误**，RSS 峰值 14.12MB→结束 13.50MB，稳态斜率 **+0.02MB/h**（基本水平）。
13. **WebSocket 帧缓冲复用**：每连接一个可增长收帧缓冲，去掉每帧 malloc/free；
   吞吐噪声内持平（161–167k msg/s）。
14. **JSON stringify 栈缓冲**：≤512B 输出在栈上构建，新增
   `194_json_stringify_large` 覆盖堆扩容路径；全套 189/189。
15. **size-class 8B 对齐**：String/event 按精确大小分配（64B/88B），不再向上取整
   到 16B class；HTTP p50 23.3→21.6µs，8 客户端 203→204k req/s。
16. **String 去 data 指针**：字节始终内联在 header 后，`WellString` 72→64B；
   String 8B new+release 91.9→81.7ns（-11%），JSON stringify 990→950ns（-4%）。
17. **String hash 惰性计算**：只在 Map key/相等比较时算 hash；String.fromInt
   101.7→88.8ns（-13%），JSON parse 1863→1800ns，stringify 950→840ns。
18. **JSON 无转义字符串快速路径**：整段 memcpy 替代逐字符解码；
   150B 对象 parse 1800→1775ns。
19. **WS/MySQL 分配清理**：WS 用帧长度构造 String（NUL 安全、省 strlen）；
   MySQL 查询包 ≤256B 走栈缓冲。吞吐噪声内持平，减少分配抖动。
20. **listen backlog 16→128**：HTTP/WS 突发 connect 容忍度提升（并发健壮性）。
21. **live 对象计数默认关闭**：只在 `WELL_RC_DEBUG=1` 时原子更新；对象
   new+release 81→69ns、String 8B 82→58ns、JSON parse 1775→1706ns。
22. **字面量按调用点缓存**：生成 C 用函数内 static 指针缓存驻留字面量；
   求值 113→96ns（vs v1 4.7×）。
23. **String 释放跳过 registry**：String 不在 oid registry/payload pin 中；
   String 8B new+release 58→49ns，String.fromInt 82→69ns。
24. **作用域退出快路径**：`well_ctx_mark` inline + `well_ctx_release_to` 空作用域
   直接返回；alloc 循环 353→338ns（vs v1 -20%）。
25. **按 panic 可能过滤源码位置更新**：仅 Call/New/除法/字段写等语句调用
   `well_source_set`；字面量循环 94→48ns（vs v1 9.3×），alloc 循环 320ns。
26. **temp journal mark 按需启用**：作用域内无 owned 临时值时不再做
   `well_temp_mark/release_to` 两次 TLS；字面量 48→17ns（vs v1 26×），alloc 273ns。
27. **JSON stringify 分块转义 + 手写整数**：stringify 820→590ns，
   parse 1706→1620ns（vs v1 -41% / -25%）。
28. **WebSocket TCP_NODELAY**：accepted socket 关闭 Nagle；回显吞吐持平，
   避免服务端推送/流式帧的合并延迟。
29. **WebSocket 帧 mask+payload 合并读取**：每帧 recv 从 4 次降到 2 次；
   回显 164.6k→173.0k msg/s（+5%），p50 24–25.8µs。
30. **WebSocket 小帧 header+payload 合并发送**：每帧 send 从 2 次降到 1 次；
   回显 173.0k→176.9k msg/s，p50 24.0–24.5µs。
31. **MySQL 小查询包合并发送**：≤512B 的 COM_QUERY 头+payload 一次 send；
   HTTP→MySQL 89–91k req/s（DB 占比高，噪声内持平），每次查询少一次 syscall。
32. **WebSocket 读侧缓冲**：一次 recv 读入整帧/多帧，典型小帧 2→1 次 recv；
   回显 176.9k→190.0k msg/s（+7%），p50 23.1–25.0µs。
33. **测试/基准工具**：`WELL_TEST_EXEC=tcc-run`、`tools/perf/*`。

## 正确性

- `.we` 用例：**189/189 通过**（新增 `194_json_stringify_large` 覆盖 stringify
  堆扩容路径；`verify-jsonstack.log`）。
- C 测试：**18/18 通过**（`verify-c-tests-batch.log`），含字面量竞态、work stealing、

- 运行方式：本机 Device Guard 拦截新未签名 exe，测试/基准用 `tcc -run` 在
  受信任的 tcc.exe 内执行；CI/普通机器仍走原生 exe。

## 遇到的问题

- Device Guard / Smart App Control 在会话中途开始拦截所有新链接 exe（包括测试
  exe、GCC），确认不是代码问题；已用 tcc-run 绕过并保留原生路径。
- String 池化初版在“池未命中 → malloc(total) → 释放按 class 复用”时越界，
  已修复为始终按 class 分配；并发 8 连接压测从偶发崩溃变为 5/5 稳定。
