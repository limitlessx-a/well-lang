### [修复] Linux CI 首轮编译失败：可移植 TLS、POSIX accept 唤醒、Cache ctx 声明、MySQL 用例跳过
- 现象：GitHub Actions 首轮 Linux job 所有非编译错误用例 build failed，报 `wellrt.c:214: error: ';' expected (got "jmp_buf")`。
- 根因 1：POSIX 分支使用编译器 TLS `__thread`，TinyCC 0.9.27 不解析（Windows 走 `__declspec(thread)` 才没暴露）；且 TCC Linux 也没有运行时 RC/自旋锁需要的 `__atomic_*`/`__sync_*` 内建函数（只会隐式声明，链接期失败）。
- 修复：新增显式 TLS 抽象 `WellTlsKey` + `well_tls_key_create/get/set`（Windows `TlsAlloc/TlsGetValue/TlsSetValue`，POSIX `pthread_key_create/getspecific/setspecific`），panic 目标、源码位置、临时对象栈、HTTP 当前请求全部改用它；POSIX 不再依赖 `__thread`。
- 顺带修掉一个真实并发 bug：TinyCC 的 `__declspec(thread)` 在 `CreateThread` 下是共享槽位（实测主线程能看到子线程写入），此前 `g_temps`/`g_current_req` 在多 worker 下会互相污染；现统一走 Win32 TLS 槽，线程结束时由 `well_temp_thread_cleanup()` 释放临时对象栈（POSIX 用 pthread key destructor）。
- 根因 2：Linux 关闭监听 fd 不会唤醒另一线程阻塞的 `accept()`，`Http.stop()`/`Ws.stop()` 后 join listener 会卡住 → 测试 “server did not stop”。HTTP/WS 监听循环改为 POSIX 用 `poll(fd, 100ms)` 后 accept（Windows 保持阻塞 accept）。
- 根因 3（CI 第 4 轮实测，唯一失败用例 `58_http_business_oid`）：`51_ws` 与 `58_http_business_oid` 都用端口 18082，Linux 上前一个进程的监听连接处于 TIME_WAIT 时，后者不带 `SO_REUSEADDR` 直接 bind 会 EADDRINUSE → panic 退出（Windows 默认允许重绑，所以本机没暴露）。HTTP/WS 监听 socket 在 POSIX 上设置 `SO_REUSEADDR`（Windows 不设，避免其“可劫持已监听端口”的语义）。
- 另外把 TLS key 的创建移到 `well_init()`/`http_lock_init()`（单线程启动期），避免两个 worker 首次使用时竞争 `g_*_key` 全局变量导致 key 不一致（临时栈泄漏/panic 目标丢失）。

### [文档] 澄清 String 拼接复杂度：单次 O(n+m)，循环累积才 O(n²)

### [优化] String 分配与空拼接快路径
- `WellString` 的 header 与字节数据合并为**一次 malloc**（`data` 指向 header 之后的内存），`string_destroy` 只 free 一次；所有 String 创建路径（字面量/新串/concat）都走该布局；
- `well_string_concat` 增加空操作数快路径：`"" + b`、`a + ""`、`null + b` 直接 retain 非空侧，不再分配/复制；
- 实测 20k 次 `s = s + "x"` 仍约 0.6s（算法 O(n²)），Bytes 约 1–2ms；本次优化只减少单次分配次数，不改变循环累积复杂度，循环拼接仍应使用 Bytes；
- 验证：115/115 + 12 个 C 测试通过；文档 language_for_ai/IMPLEMENTATION/README 同步说明。

### [修复] P0-1：对象池 size class 复用导致堆越界（审计 B16）
