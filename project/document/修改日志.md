### [修复] P0-1：对象池 size class 复用导致堆越界（审计 B16）
- 根因：对象池按 16B size class 复用，但 `well_new` 原先按**精确 size** 分配；同一 class（如 5：65–80B）混放 72B/80B 的事件对象时，72B 分配被 80B 对象复用 → `memset(...,80)` 与字段写入越界 8 字节
- 触发条件：之前保留 `WellObj.graph_edges` 时事件尺寸恰好都是 80B；删除该 reserved 字段后 `WsMessageEvent/WsBusinessEvent` 变为 72B，与 80B 事件同 class → `60_ws_business_oid` 稳定 `0xC0000374`（曾被误判为 WS 关闭路径 UAF）
- 修复：`well_new` 新分配统一按 class 整块大小（`pool_class(size)*16`）申请并记入 `alloc_size`；池内任意块都能安全承载同 class 的最大对象
- 同时永久删除 `WellObj.graph_edges` reserved 字段（对象图早已为 no-op 桩），对象体积减小
- 验证：`60_ws_business_oid`/`61_ws_concurrent` 各 8 轮压力全过；HTTP 压测 3 轮通过；全量 97/97 + C 测试

### [安全] static 引用字段禁止 event 类型
- checker 新增 `check_static_field_type`：static 引用字段的类型中若出现 event（直接声明、容器元素、或经 struct 字段递归可达）→ 编译错误 `event type E is not allowed in static fields`
- 原因：`emit` 会把 event 的 oid 从 0 改写为 `IdUtil` 生成的非 0 id；static 持有的 event 会因此变成"非装配期 oid"，默认 TTL 开启后可能被整组清理 → 悬空
- 测试：`97_static_event_field`（直接声明）、`98_static_event_container`（`Array<GoEvent>`）、`99_static_event_nested`（struct 字段间接）
- 验证：97/97 + C 测试；文档 IMPLEMENTATION/README/路线图/审计 B21/修改日志

### [安全] static 生命周期改用"装配期 oid"而非硬编码 0
- 新增 `well_static_owner_oid()` / `well_static_owner_set()`：static 数据属于**启动 ctx 的 oid**（当前 0，未来可改为其它系统 id）
- 写权限：`well_static_check_write` 改为"未冻结 且 `ctx.oid == 装配期 oid`"；`well_run_loop()` 启动时调用 `well_static_freeze()` 冻结，运行期任何写 panic `static field S.f is read-only (assembly oid=..., ctx oid=...)`
- 值校验：`well_static_set_ref` 要求非 String 值 `value.oid == ctx.oid`（装配期 oid），防止启动期把 oid≠装配期 的对象塞进 static 后被 TTL 清理造成悬空
- `well_statics_init()` 的构造上下文改用装配期 oid；生成的 `main` 在 entry run 前 `well_static_owner_set(ctx.oid)`，随后初始化 static 默认值
- TTL/强制清理豁免从"跳过 oid 0"改为"跳过装配期 oid"（当前行为不变，未来系统 oid 改变时自动跟随）
- 测试：`92_static_write_panic` 更新 panic 文案；全量 94/94 + C 测试；手册验证启动期 `new E(123)` 塞入 static 会 panic `value oid 123 must equal assembly oid 0`
- 文档：IMPLEMENTATION/README/路线图/审计 B18/B19/B20

### [修复] `Array.sort()/reverse()` 补 oid 写检查
- 此前 `sort/reverse` 直接重排 items，绕过 `well_check_oid`：在 handler 里可以对启动期创建（oid=0）的数组静默排序/反转，形成无锁的全局数据竞争
- 现在 `well_array_sort/well_array_reverse` 接收 `ctx`，先做 `well_check_oid`（where=`Array.sort` / `Array.reverse`），与 push/set/clear 等容器写操作一致；handler 里对 oid 不匹配的数组调用会 panic `well oid violation`
- 测试：`89_array_oid_panic`（启动期构造 static 数组，handler 里 sort/reverse 均被隔离 panic，rc_debug=0）
- 验证：89/89 + C 测试；文档 IMPLEMENTATION §3 Array 方法补充 oid 检查说明

### [功能] `Model.cleanup(ttlMs)` 手动清理 API + 环/跨 oid 约束文档

### [修复/优化] 移除对象图全局锁；修复调度器丢失唤醒导致的并发 hang
- 对象图是死代码：`well_graph_add_edge` 一直是空实现，但 `well_graph_remove_edge`/`well_graph_clear_edges` 仍在每次引用覆盖和**每次对象销毁**时获取全局 `g_graph_lock` 并扫描空链表——纯开销，且是所有 worker 的串行点
- 处理：删除 `WellEdge`/`graph_reaches`/`clear_edges` 等死代码，add/remove 改为空实现；`well_release` 不再调用 clear_edges（每对象销毁少一次全局锁）；`WellObj.graph_edges` 保留为 reserved 字段（实验表明删除该字段会改变对象布局，触发 WS 关闭路径上一个既有的堆损坏风险，需单独排查，见审计文档）
- 修复调度器丢失唤醒：main worker 的退出条件是 `pending==0 && service==0`，但完成路径用 `signal` 可能唤醒其他 worker，main 永远睡下去；新增 `sched_notify()`：该谓词可能成立时改用 `broadcast`。此前 Windows cond 是 10ms 轮询掩盖了此 bug，改原生条件变量后暴露（`32_model_hash` 在 `WELL_WORKERS=4` 下稳定 hang，已定位：4 个 worker 全部睡在 cond 上、pending=0）
- 验证：`32_model_hash` workers=4 连续 10 次无 hang、`60_ws_business_oid` 5 次通过、全量 84/86（52_mysql/53_mysql_pool/C mysql_conn_test 因本机 MySQL 服务未运行失败，与本次改动无关）
- 基准：单请求 min 33.7 µs（raw C 26.3 µs，机器噪声内与上轮持平）；4 客户端 48–49k req/s（本机负载与上轮不同，未观察到量级变化）

### [修复] P0 编译器正确性检查（审计 A1–A6）
- **A1 返回类型检查**：`return` 的值必须可赋给声明的返回类型（`func f(): int { return "abc"; }` 现在编译错误 `cannot assign String to int`，此前会静默输出指针值）

- **A6 容器字面量作实参**：改为明确 checker 错误（提示先赋给变量），不再抛 Python traceback
