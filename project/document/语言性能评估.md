# 语言性能评估

日期：2026-10-24  
机器：Intel i5-12400F（6P/12T），Windows 11 26200，同机测试。  
对比语言/实现对：**Well v1、Well v2、Well v3、C、C++、Java、Go、Erlang**。

> v3 位于 `E:\Work\WellLangV3`，是基于 v1 的性能优化工作区。
> v3 不带自己的 TCC，本文 v3 数据使用其推荐配置：
> `WELL_CC=project/tool_ai/clang.cmd`（Zig/Clang）、`WELL_CFLAGS=-O2 -fwrapv -flto`。
> v2 的 Release 为 `--release`，即 `-O2 -fwrapv -DWELL_NO_OID_CHECK=1`。
> v1 使用自带 TCC；v2 TCC 使用默认 TCC。

## 1. CPU：数组访问（2000 万次）

负载：1024 个 `long`，循环 2000 万次 `acc += a[i & 1023]`，输出 acc。

| 实现 | ns/iter | 相对 C |
|---|---:|---:|
| C（Clang -O2） | **0.200** | 1.00× |
| Go 1.27 | 0.257 | 1.29× |
| C++（Clang -O2） | 0.261 | 1.31× |
| Java 21 | 0.380 | 1.90× |
| **Well v2 Release** | **~0.40** | **~2.0×** |
| Erlang OTP 29 | 2.98 | 14.9× |
| Well v2 TCC | 2.7 | 13.5× |
| **Well v3 LTO（复测）** | **5.6** | **28.0×** |
| Well v1 | 75.1 | 375× |

结论：

- v2 Release 已接近 Java/C++，约为 C 的 2×；
- v2 TCC 约为 v1 的 28×，v2 Release 约为 v1 的 188×；
- v3 LTO 比 v1 快约 **13.4×**，但仍比 v2 TCC 慢约 **2.1×**、比 v2 Release 慢约 **14×**；
- v1 仍是旧 codegen/runtime，数组访问慢两个数量级。

## 2. CPU：纯求和循环（1 亿次）

负载：`for (i = 0; i < 100000000; i++) acc += i`。

| 实现 | ns/iter | 说明 |
|---|---:|---|
| C / C++（Clang -O2） | ~0 | 被优化成闭式，无有效数据 |
| Well v2 Release | ~0 | 同样被优化掉 |
| Well v3 LTO | ~0 | 同样被优化掉 |
| Go 1.27 | 0.248 | |
| Java 21 | 0.261 | |
| **Well v2 TCC** | **0.84** | |
| Erlang OTP 29 | 1.34 | |
| Well v1 | 70.0 | |

说明：该负载对优化编译器不公平，主基准看第 1 节数组访问。v2 TCC 比 v1 快约 83×。

## 3. 短生命周期分配（200 万次）

语义不完全相同：C/C++ 为 `malloc/new` 后释放；Go/Java 分配后保留引用；Erlang 为 binary copy；Well 为对象 new+release 并逃逸到字段。

| 实现 | ns/op |
|---|---:|
| Go 1.27 | **23.8** |
| C（Clang -O2） | 25.5 |
| C++（Clang -O2） | 27.1 |
| Java 21 | 30.8 |
| **Well v2 Release** | **39.0** |
| **Well v3 LTO（复测）** | **60.0** |
| Well v2 TCC | 100.5 |
| Well v1 | 223.5 |
| Erlang OTP 29 | 362.6 |

结论：

- v2 Release 约为 Java 的 1.27×、C 的 1.53×；
- v2 Release 约为 v1 的 5.7× 快；
- v3 比 v1 快约 3.7×，但比 v2 Release 慢约 1.54×。

## 4. 小容器创建（200 万次）

语义不完全相同：C++ 为 `new vector`，Java 为 `ArrayList`，Go 为 slice+append，Erlang 为 list，Well 为 `Array<int>`+push+字段逃逸。

| 实现 | ns/op |
|---|---:|
| Erlang OTP 29 | **5.9** |
| Go 1.27 | 7.5 |
| Java 21 | 23.0 |
| **Well v2 Release** | **30.0** |
| C++（Clang -O2） | 59.2 |
| Well v2 TCC | 87.0 |
| **Well v3 LTO（复测）** | **~119** |
| Well v1 | 284.5 |

结论：

- v2 Release 比 Java 慢约 1.3×，比 C++ vector 快；
- v2 Release 约为 v1 的 9.5×；
- v3 比 v1 快约 2.4×，但比 v2 TCC 慢约 1.4×，比 v2 Release 慢约 4.0×。

## 5. HTTP keep-alive（8 clients，小响应 `ok`）

v2/C/C++/Go/Java/Erlang 为同一轮；v1、v3 为单独探针，不能与同轮数值做严格同轮比较。

| 实现 | req/s | p50 | RSS | 备注 |
|---|---:|---:|---:|---|
| C（Clang -O2） | **258.1k** | 20.6 µs | 4.3 MB | 手写 thread-per-conn |
| C++（Clang -O2） | 257.3k | 19.1 µs | 4.3 MB | 同源 |
| **Well v2 Release** | **238.3k** | 21.7 µs | **4.8 MB** | |
| Well v2 TCC | 223.2k | 21.4 µs | 13.7 MB | |
| **Well v3 LTO（复测）** | **160.6k** | 28.8 µs | 9.4 MB | Clang LTO |
| Go 1.27 `net/http` | 158.8k | 33.7 µs | 17.6 MB | 标准库 |
| Well v1 | 150.4k | 30.2 µs | 9.7 MB | 单独一轮，旧 server |
| Java 21 `HttpServer` | 99.9k | 286.7 µs | 394 MB | 固定线程池 |
| Erlang `gen_tcp` | 89.1k | 41.7 µs | 53.3 MB | 每连接一进程 |

结论：

- v2 Release 约为 C/C++ 的 92%，差距约 8%；
- v2 Release 约为 Java 的 2.4×、Go 的 1.5×、v1 的 1.58×、v3 的 1.48×；
- v3 HTTP 与 Go、旧 v1 同档，明显低于 v2。

| 维度 | 快 → 慢 |

| CPU 数组访问 | C ≈ Go ≈ C++ > Java ≈ v2 Release ≫ Erlang > v2 TCC > v3 LTO ≫ v1 |

## 10. 结论

1. **v2 相对 v1 是量级提升**：数组约 28×（TCC）/188×（Release）、求和约 83×、对象分配约 5.7×、容器约 9.5×、HTTP 约 1.58×。
2. **v2 Release 已进入 C++/Java 档位**：数组、对象、容器、JSON 达到或超过 Java；HTTP keep-alive 约为 C/C++ 的 92%；WS 吞吐接近 Java，但 p50/RSS 更好。
3. **v3 是 v1 之上的性能工作区**：复测后相对 v1 数组约 **13.4×**、对象约 **3.7×**、容器约 **2.4×**、HTTP 约 **1.07×**；但本次 LTO 构建仍全面慢于 v2，尚未达到 v2 Release 水平。
4. **v3 报告和本文不矛盾，但不能直接跨 workload 对比**：
   - v3 报告分配 **27 ms** 是“替换并保留 1024 个对象”；
   - 本文分配 **120 ms（60 ns/op）** 是“200 万次 new + release + 字段逃逸”；
   - v3 报告 CPU **66 ms** 是整数递推/取模，本文数组访问是 **112 ms**；
   - 两者测的不是同一种行为，不能把 27 ms 和 60 ns/op 直接比较。
5. **v2 TCC 仍明显慢于 v2 Release**，适合开发/快速编译；性能场景应使用 `--release`。
6. **v3 没有 TCC 数据**：v3 不带 TCC，本文 v3 只列 Clang LTO 优化构建。
7. 跨语言数字受语言语义（RC vs GC、栈/区域、容器实现、HTTP server 实现）影响；分配、容器、HTTP/WS 不是完全等价的实现。
