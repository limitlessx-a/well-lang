## 2. 新发现 P0（3 条，均实测）

### R2-FE-01 / R2-CG-01（跨域）null struct/event 字段读直接段错误

```we
struct S { x: int; }
controller Main { run() { var s: S = null; print(s.x); } }
entry Main;
```
- `check` 通过；`run` → **rc=0xFFFFFFFF（访问违例）、stdout/stderr 全空**，无 panic、无 `file:line`。
- 对比：**写**路径 `s.x = 1` 有保护 → `well panic: null object write`（exit 70）。
- 相关：`var e: E = null; print(e.n);`、`func get(s:S){return s.x;} get(null)` 同样崩溃。
- 根因：`codegen.py:424` 字段读生成 `(obj)->f_x`，没有 null/oid 检查；写路径 `codegen.py:1392` 有 `well_check_oid`。
- 建议：读路径与写路径对称 —— 生成 `well_check_oid(obj, ctx, "field read")`（或 runtime 提供 `well_field_read` 包装）；至少 panic 带 `file:line`。

### R2-01（codegen）枚举成员宏名歧义 → 静默错误值

```we
enum A { B_C = 12; }
enum A_B { C = 22; }
controller Main { run() { print(A.B_C, A_B.C); } }
entry Main;
```
- `check` 通过；`run` 输出 **`2222`**（期望 `12 22`）；TCC exit 0、GCC 同样 22（`warning: 'E_A_B_C' redefined`，driver 不展示）。
- String 枚举同理（`firstsecond` → `secondsecond`）。
- 根因：`codegen.py:1578-1590` 用 `E_<enum>_<member>` 拼接，分隔符 `_` 与用户名字符集冲突。
- 建议：组件**单射转义**（如 `_` → `_x`）后拼接，或使用保留分隔段（`E_<enc(enum)>_$_<enc(member)>` 风格）；同时修 helper 名（R2-08）。

### R2-HTTP-01（模块）慢 handler 超时后 `Http.respond` → use-after-free

- 复现程序 `tool_ai/tmp/round2/modules/r2_http_uaf.we`：路由 handler 忙等 9s 后 `Http.respond(reqId, ...)`。
- 客户端 5s 先收到 **504**（连接被清扫线程释放）；handler 继续运行，9s 时 `Http.respond` 访问已释放的 `req->conn`/`conn->lock` → **exit 0xC0000005（3221225477）**，2/2 稳定；Lead 独立复现 1/1，stdout 停在 `bg9: responding late`。
- 影响：**"业务处理耗时 >5s 再异步响应"是文档鼓励的用法**，直接崩进程；远程可触发（任意慢请求）。
- 根因：`well_http.c:951-974` 504/超时路径释放 conn；`well_http.c:524-541` 的 `http_respond_claimed` 仍用 `req->conn`；H8 的请求 pin 没覆盖 conn 生命周期（或 pin 时机不足）。
- 建议：respond 前校验请求状态（`revoked/timed_out`）并返回错误；conn 在请求引用归零前不释放（引用计数），或 504 后把请求标记为 detached、respond 变成显式失败（语言层返回 bool/错误）。

## 4. 新发现 P2 / P3（按域归纳）

### 4.1 前端（12 条）
- **R2-FE-06** parser 深度 64 共用计数器：63 层嵌套调用即报 `expression nesting too deep`（合法程序被拒），嵌套块误报 expression 类型；规范未写上限。
- **R2-FE-07** 多诊断粒度：声明级（struct/static 字段）仍只报第一条，与规范"按声明收集"不一致。
- **R2-FE-08** `cur_pos` 跨 attempt 泄漏：无自身位置的错误（如 `entry Nope`）沿用上一个失败单元的位置（实测指到 struct 字段 1:12）。
- **R2-FE-09** 重复声明/跨文件重复诊断仍靠启发式：同文件重复指到第一函数内递归调用；跨文件重复 JSON 的 file 归到主文件（message 才含真实文件）。
- **R2-FE-10** const 循环/自引用不检测：`const A:int=B; const B:int=A;` check 通过、build C 宏未定义。
- **R2-FE-11** `case true` 与 `case 1` 重复不检测（C 阶段 `duplicate case value`）。
- **R2-FE-12** 内置名可声明但解析被内置静默遮蔽（`func print()` 永远不可达；`Model` 结构体可声明但不能以 `Model.get` 调）。
- **R2-FE-13** `Host.log(void 表达式)` 通过 checker，运行输出 `0`；**R2-FE-14** `print(struct/容器)` 输出指针地址。
- **R2-FE-15** int/long 最小值字面量无法直接写（`-2147483648` 报窄化；`-9223372036854775808` 报越界）。
- **R2-FE-16** 文档未同步：`语言规范.md:302` 仍写三元"不做强校验"、`待开发功能-优先级.md:115/156/297` 仍写 IO 退出码偏差（实际已修）。
- **R2-FE-17**（已知限制确认）`T?` 仅解析不检查（已文档标注）。

### 4.2 codegen / driver（4 条）
- **R2-CG-07** `__` 组合命名碰撞：`namespace A{b}` vs `func A__b`、`ns A{b__c}` vs `ns A__b{c}`、`static S{f}` vs `func S__f` 等 4 类，check 通过、build 报 C `redefinition`（Lead coll1 同源）。
- **R2-CG-08** 枚举成员名覆盖 helper：`enum X { _toString = 1; }` → `E_X__toString` 宏与同名 helper 函数冲突，C 编译失败。
- **R2-CG-10** `check` 跨文件重复声明定位到错误文件（位置落在主文件同名标识符）。
- **R2-CG-11** 构建产物 `<stem>_<hash8>` 无清理：本机 `compiler/build/` 373 个 `.c` + 169 个 `.exe`（约 13 MB），无 GC/`--clean`；hash 前缀理论碰撞 P3。

### 4.3 runtime core（3 条 + 5 P3）
- **RN2-03** event payload pin 不按 emit 次数计数：同一 event emit 两次，第一次 release 的 unpin 清空全部 pin，第二个排队 event 失去 TTL 保护（确定性演示 payload 被回收）。
- **RN2-04** R-02 断链语义：入口引用/超过 128 深度时静默返回 NULL，调用方无法区分"无此对象/环/超深"。
- **RN2-05** `well_event_shutdown` 在非 quiescent（有 worker 运行）时跳过清理的契约未文档化。
- P3：清理 panic 后 `cleaning` 永久置位；pin oid0/emit 额外开销；OOM panic 路径残余；32 位/POSIX 原子与对齐未验证；int 字段截断行为文档化。

### 4.4 模块（12 条 P2 + 9 P3）
- **HTTP**：流水线时 `path` 在 memmove 后使用导致 405 误报 404（R2-HTTP-04）；残量 >16KB 误 400（R2-HTTP-03）；重复/空 Host 接受（R2-HTTP-05）；`Content-Length :`（冒号前空格）不识别（R2-HTTP-06）；响应体按 `strlen` 发送 → 内嵌 NUL 截断（R2-HTTP-07）。
- **WS**：协议错误后 close handler 收到 `1006`（应 1002/1003/1009，R2-WS-01）；握手不校验 Upgrade/Connection/Version、重复 Key 也 101（R2-WS-02）；文本帧/`Ws.send`/close reason 内嵌 NUL 截断（R2-WS-03）。
- **MySQL**：auth-switch 包 `plen-k` 下溢 OOB 且畸形包可连接（R2-MYSQL-02）；queryJson 二进制列输出非 UTF-8（R2-MYSQL-03）；池 acquire 3s 超时被 COM_PING 拖到 15.1s（R2-MYSQL-04）。
- **POSIX**：`ws_wait_readable` 只认 `POLLIN`，RST 延迟到 60s idle（R2-POSIX-01）；HTTP/WS `sockaddr` 用 `unsigned long addr` 布局错误（仅 INADDR_ANY 侥幸可用）。
- P3：accept 任意失败即永久退出；shutdown 防御路径忽略引用；`Ws.close` 锁外 shutdown fd 竞态；shutdown 兜底无写锁；文本帧不做 UTF-8 校验；MySQL >16MB 包不续包；`cols==0` calloc(0) 误报 OOM；closePool 超时泄漏（已文档）；405 缺 `Allow` 头。

### 4.5 Lead 交叉复核补充
- **null 引用读取语义不一致（P2）**：null String/Bytes/Array/Map/Linked 的读操作（`.length`、`[]`、`get`、`+`、`trim`）静默当空/0；写操作（push/set）panic 带位置；struct 字段读则段错误（P0）。建议统一为"读也 panic（带位置）"或文档明确 null 安全语义。
- **深递归无保护（P2）**：`f(100000)` → 进程直接崩溃（exit -1），无 panic；与 R-01/R-02 同属栈溢出类，但由用户代码触发。建议文档声明 C 栈限制，或在生成函数入口做深度计数。
- **死代码（P3）**：parser 不支持 `& | ^ << >>`，但 checker/codegen 留有对应分支（`checker.py` 运算符表、`codegen.py` 兜底），不会触发；清理或实现。
- **严格 C99 违约（P1，同 R2-CG-06）**：`gcc -std=c99 -pedantic-errors` 失败；"生成 C 使用 C99"的文档需改为 GNU C 或消除语句表达式。

## 5. 建议修复优先级
